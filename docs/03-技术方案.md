# 03 · 技术方案 【提案】

> 这是六个项目里 RAG 工程深度最大的一个——解析、切块、引用溯源、幻觉抑制、
> 评测全套都要真做。简历价值主要兑现于此文档。

## 架构

```
上传 → 解析层 → 条款树 → ┬─ 规则引擎（确定性审查）
                          ├─ LLM 审查层（引用约束生成）
                          └─ 模板差异层（条款树 diff）
                                     ↓
                            报告聚合 + 引用校验门
                                     ↓
                     前端报告页（原文-结论联动高亮）
```

## 分层设计

### 1. 解析层（最脏最值的活）

- PDF/DOCX：文本层直取；扫描件：OCR（云 API，双语）；
- **条款树构建**：正则+布局启发式识别"第X条/一/1./(1)"层级，LLM 兜底处理非标编号；
  条款树节点带页码/坐标，支撑前端点击定位；
- 失败兜底：解析置信度低的文档降级为"线性分块+段落定位"，报告标注"精确定位不可用"。

### 2. 规则引擎（确定性通道）

- 规则 = 检测函数 + 适用条件 + 例外清单，纯 TS，可单测——直接沿用工具链项目的
  规则组织方式（repo-inject-guard 的 detector 结构）；
- 全部规则带单测 + 快照测试，新增规则不许打破既有例外（回归即红线）。

### 3. LLM 审查层（语义通道，防幻觉是第一设计目标）

- 每条审查任务 = 条款子集 + rubric prompt，要求输出 JSON：结论/等级/引用片段/建议；
- **引用校验门**（关键）：输出里的引用片段与原文做规范化字面比对
  （去空白/全半角归一），不过则重试一次，再不过该条丢弃并记录——
  "宁缺勿错"以代码而非 prompt 约束执行；
- 温度 0 + 结构化输出 schema 校验（zod 风格），非法 JSON 直接重试；
- 每份合同的 LLM 调用按条款分组并发，30 页合同目标总耗时 <60s。

### 4. 模板差异层

- 条款树对齐（类型匹配 + 相似度阈值）→ 结构化 diff → 语义偏离由 LLM 判定并同样过引用门。

## 评测（eval-spec，本项目的简历核心）

**golden-corpus**：40 份合同（自制改写 25 + 试点脱敏 15），每份人工标注：
条款位置真值、风险点清单、缺失条款清单。指标：

| 指标 | 定义 | v0.1 门槛 |
|---|---|---|
| 条款召回 | 抽取条款命中真值比例 | ≥0.90 |
| 风险精确率 | 报出风险中真风险比例 | ≥0.85（宁缺勿错的量化） |
| 引用有效率 | 引用校验通过且语义相符比例 | ≥0.95 |
| 缺失检测 | 缺失条款召回 | ≥0.80 |
| 端到端时延 | 30 页合同 | ≤60s |

CI：golden-corpus 全量回归进 GitHub Actions（agentbench-local 任务集格式），
prompt/模型/规则任一变更触发。**这份评测基准本身可开源发布**——
"中文合同审查评测集"，填补公开空白，独立成为仓库资产。

## 技术栈

TypeScript + ESM；服务端 Node；前端 Vite + 报告页重交互（原文联动高亮）；
存储：Postgres + 对象存储（默认即删策略）；部署同 saas-starter 私有化变体
（Docker Compose 一键起——私有化版本的地基）。

## 成本模型

单份 30 页合同：OCR（如需）¥0.1-0.3 + LLM 约 ¥0.2-0.5 → 对 ¥9.9/份毛利 90%+。
团队版按 100 份/月计成本 <¥100，可忽略。
